# Review fixes and boundaries

The local dashboard is described in [DASHBOARD.md](DASHBOARD.md). This implementation also addresses the six findings in the initial review.

- **Build and coverage:** the missing package did not exist in Git history. A replacement registry now contains eight passive checks and four explicit WSTG 4.2 references. It makes no ASVS-completeness claim. The ignore rule targets `/coverage/`, not source packages. Explicit check execution records are required for passes; unknown codes and unexecuted checks remain visible.
- **Account identity:** login validates the configured `identityPointer` against the supplied username and captures a stable `principalPointer` (default `/id`). Two distinct canonical principals are required; IDs are rechecked around verification. Set the pointer to the application's immutable subject field, not an alias or display name. Duplicate account configuration IDs are rejected.
- **Cleanup recovery:** migration `006_cleanup.sql` adds durable, owner-bound cleanup intents. Production persists before creation, with no account credentials stored in the intent. Up to ten extra DELETE requests are reserved per assessment, each bounded to 15 seconds and still gated by current policy and active-testing permission. Completion requires marker absence (`404`), including a follow-up marker DELETE after `200`/`204`; `202` remains pending. Uncertain creation, revocation, failure and cancellation can leave obligations requiring reconciliation. A later authorized assessment checks these before creating new resources; unmatched owners or changed rules remain held. This is a conservative contract requiring an application-specific marker cleanup endpoint, not a universal deletion protocol.
- **Visibility:** `npm run cleanup:list` and generated `CLEANUP.md` expose pending obligations. Failed jobs can be retried under existing lease behavior. A completed assessment with pending cleanup needs a new reviewed assessment/revision or operator action; there is not yet a standalone cleanup scheduler. Process-death recovery relies on the journal rather than a claim that `finally` always runs.
- **Retention:** eligible observation payloads, tool/agent records, hypotheses, related non-held findings/evidence and job results are purged transactionally in bounded batches; job identity/deduplication metadata remains. Programs with pending cleanup and findings in review/verification/submission are held. The sweep reconciles Markdown exports and retries pending exports on subsequent application. Backups, external downloads, operator NOTES, dashboard history and unrelated legacy/unlinked data require separate retention policies. Late model writes cannot recreate purged payloads.
- **CI and reporting:** browser tests and the detector gate are part of CI. Passive off-site redirects and incompatible wildcard CORS configurations are informational observations, not automatically classified exploits.

## Still outside this implementation

Owned-staging/real-mailbox validation, authenticated team policy approval, independent network egress enforcement, fleet-wide revocation, role-aware secret services, scheduled campaign/retest orchestration, complete evidence key management and production deployment remain later milestones. The new interface deliberately exposes only passive public web checks. Passing local fixtures does not establish full penetration-testing coverage or production isolation.
